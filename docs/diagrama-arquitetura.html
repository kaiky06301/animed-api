Animed — arquitetura da solução na Azure

Sprint 3 · DevOps Tools & Cloud Computing · Opção 1: ACR + ACI — aplicação e banco 100% em container, provisionados por Azure CLI

Fluxo — o que acontece, na ordem

#Passo
1A equipe roda criar-recursos-azure.ps1. O Azure CLI cria o resource group, o registro e os container instances — nada pelo Portal.
2az acr import traz a imagem oficial do Oracle XE do Docker Hub para dentro do ACR.
3Sobe um container kaniko que clona este repositório do GitHub — o código-fonte é o contexto do build.
4O kaniko executa o Dockerfile, compila o JAR e publica animed-api:1.0 no ACR. Depois é removido.
5O ACI da aplicação puxa a imagem da API do ACR e sobe o container na porta 8080.
6O ACI do banco puxa a imagem do Oracle do ACR e sobe o container na porta 1521.
7A aplicação conecta no banco por JDBC. O Flyway cria o schema e o CRUD passa a gravar em TB_TUTOR e TB_PET.
8Tutor e veterinário acessam pelo FQDN público do ACI — a solução não roda em localhost.

Decisões de arquitetura

PontoDecisão e motivo
Opção da entregaACR + ACI. Aplicação e banco em container — sem misturar com App Service ou banco PaaS.
Build sem DockerACR Tasks é bloqueado nesta subscription e as máquinas não têm Docker Desktop. O kaniko constrói a imagem dentro da própria Azure.
Container não-rootO Dockerfile cria o usuário animed e declara USER animed: o processo Java não tem privilégio administrativo.
SegredosSenha do banco e segredo JWT entram como --secure-environment-variables: não estão no código nem aparecem no az container show.
Schema versionadoO Flyway aplica 12 migrations na primeira subida — o banco nasce pronto e reproduzível, sem DDL manual.
Dois containers separadosBanco e aplicação reiniciam de forma independente; o ACI do Oracle guarda o estado que o vídeo comprova por SELECT.
Regiãobrazilsouth, dentro da cota de 6 cores do Azure for Students (2 banco + 1 app + 2 do build temporário).
